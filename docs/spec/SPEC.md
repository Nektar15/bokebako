1. 本書の目的と位置付け

本書は、Webサービス「ぼけばこ」の初期開発（MVP）について、実装する画面と機能、システム構成、開発体制とスケジュール、ならびに開発費用の内訳を定め、発注者様と開発者の間で開発範囲を確定することを目的とします。

本書に記載のない機能は初期開発の対象外とし、追加が必要となった場合は別途協議のうえ、見積を追加します。文言・デザインの細部は、開発着手後のデザイン確定フェーズで調整します。

1.1 前提条件

- 開発費用は合計5,000,000円（税抜）とし、エンジニア2名・約3ヶ月の体制で実施します。

- サーバーはXserverレンタルサーバー「ビジネス」プラン（月額3,960円〜）を使用します。サーバー・ドメインの契約名義は発注者様とし、契約費用は開発費に含みません。

- サービス名は「ぼけばこ」とします。ドメインは第一希望 bokebako.com / bokebako.jp、第二希望 bokebako24.com / bokebako24.jp の順で取得を試みます。

- サーバーサイドはPHP / CodeIgniter 4で実装します。CSS（見た目）の実装方針はデザイン確定後に決定します。

- 月間100万PV規模のアクセスに耐える設計を行います（詳細は第4章）。

- AIによる投稿判定にはOpenAI「GPT-5 nano」を使用し、疑わしい投稿のみを判定対象とします（詳細は第9章）。

- ロゴ・キービジュアル・画面デザイン（カンプ）は発注者様よりご支給いただくか、別途デザイン費で対応します。

2. サービス概要

2.1 サービスの定義

「ぼけばこ」は、会員登録不要で、24時間限定の大喜利を誰でも開催できるWebサービスです。SNSとして内部にコミュニティを構築するのではなく、X（旧Twitter）を集客・拡散基盤として利用し、「Xで見つける → ぼけばこで遊ぶ → Xへ戻す → 次のぼけばこが生まれる」という循環そのものをプロダクトとします。

| **項目** | **内容** |
| --- | --- |
| **サービス名** | ぼけばこ（画面上のキャッチコピー等では「24時間」を訴求） |
| **ドメイン** | 第一希望：bokebako.com（および bokebako.jp） 第二希望：bokebako24.com（および bokebako24.jp） ※ 取得可否は契約時に確認。.com と .jp を両方取得し、片方は転送設定とすることを推奨 |
| **対象ユーザー** | Xを利用する一般ユーザー（開催者・回答者・閲覧者） |
| **利用条件** | 会員登録・ログイン不要。開催者は管理用トークン（ブラウザ保存）と合言葉で本人確認 |
| **収益モデル** | スポンサー広告（上部・下部枠）。一般ユーザー課金は行わない |
| **対応端末** | スマートフォン優先（レスポンシブ対応）。PC・タブレットでも閲覧・操作可能 |
| **対応ブラウザ** | iOS Safari、Android Chrome、PC Chrome / Edge / Safari / Firefox の各最新版 |

2.2 基本フロー

- 開催者がお題を作る（テンプレート・ランダムお題も利用可）

- 24時間の募集を開始し、専用URLをXでシェアする

- 参加者が匿名で回答する（回答後は他の回答を閲覧可能）

- 24時間経過で自動締切

- 開催者がベスト回答を最大3件選択する（72時間以内）

- 結果ページが生成され、Xでシェアされる

- 参加者・閲覧者が新しい大喜利を開催する（循環）

2.3 実装しない機能（サービス方針）

仕様膨張を防ぎ、上記の循環に集中するため、以下は初期開発では実装しません。

- ユーザー会員登録、ユーザープロフィール、フォロー、DM、内部タイムライン

- サービス全体ランキング、ユーザーランキング、参加者による投票・いいね・点数・コメント

- ポイント、賞金、一般ユーザー課金、決済

- ネイティブアプリ、画像投稿、動画投稿

- 全投稿を常時対象とするAI検閲、独自AIモデル、企業向け広告セルフサービス

3.4 セキュリティ要件

- CSRF対策（CodeIgniter標準のCSRFトークン）、XSS対策（出力エスケープ）、SQLインジェクション対策（クエリビルダ／プリペアドステートメント）

- 管理画面はIPアドレス制限（任意）＋ID/パスワード＋ログイン試行回数制限。パスワードはbcryptでハッシュ化

- 開催者トークン・合言葉・投稿元識別情報はハッシュ化して保存。生IPアドレスは一定期間後に削除

- 全ページHTTPS化（HTTP→HTTPSリダイレクト）、セキュリティヘッダー設定

- 回答・開催・通報のレート制限（IP／匿名ブラウザID単位）

- OpenAI APIキー等の秘密情報は環境変数（.env）で管理し、リポジトリに含めない

4. 100万PV対応方針

月間100万PVは1日あたり約33,000PV、平均で毎秒0.4リクエスト程度ですが、本サービスはXでの拡散を前提とするため、特定の大喜利がバズった際に短時間へアクセスが集中します。そのため「平均」ではなく「瞬間的なピーク（平均の20〜50倍）」に耐えることを設計目標とします。

| **設計目標** 月間100万PV（日間3.3万PV）を安定して処理すること ピーク時 毎秒20リクエスト程度の動的アクセスを、共有サーバー上で応答2秒以内に処理すること 結果ページ・募集終了ページなど「更新頻度の低いページ」は動的処理を行わず配信すること |
| --- |

4.1 具体的な対策

| **対策** | **内容** | **効果** |
| --- | --- | --- |
| ページキャッシュ | 結果発表ページ・募集終了ページ・紹介ページ・規約類はCodeIgniterのページキャッシュで静的HTMLとして配信。結果確定時にキャッシュを生成・更新 | PVの大半を占める閲覧系リクエストのDBアクセスをゼロにする |
| 回答画面の軽量化 | 回答画面（募集中）は残り時間・回答数のみを軽量APIで取得し、本体HTMLはキャッシュ配信 | バズ時の同時アクセスに対応 |
| OGP画像キャッシュ | 募集用・結果用OGPは生成時に画像ファイル化。回答シェア用OGPは初回アクセス時に生成しファイルキャッシュ（事前大量生成はしない） | Xクローラーからの画像リクエストをCPU負荷なく処理 |
| DB最適化 | スラッグ・状態・日時にインデックス設定。回答数・PVはカウンタ列に集約し、集計クエリを避ける | 回答一覧・管理画面の応答速度確保 |
| OPcache / 静的資産 | PHP OPcache有効化。CSS/JS/画像はバージョン付きURLで長期ブラウザキャッシュ | PHP実行コストと転送量の削減 |
| PV計測の非同期化 | PVカウントはリクエスト処理内で都度UPDATEせず、ログ集約→cronで集計 | 書き込み負荷の平準化 |
| CDNの利用（推奨） | Cloudflare（無料プラン）をDNS前段に配置し、静的資産・OGP画像・キャッシュ済ページをエッジ配信 | サーバー到達リクエストを大幅に削減。DDoS耐性も向上 |
| レート制限 | 回答・開催・通報に匿名ブラウザID／IP単位の制限を実装 | BOT・スクリプトによる負荷を抑止 |

4.2 負荷試験

リリース前にステージング環境で負荷試験（k6等）を実施し、回答画面・回答投稿・結果ページについて、毎秒20リクエストの負荷で応答時間とエラー率を確認します。

4.3 将来の拡張

レンタルサーバーの性質上、CPU・メモリの上限を超える突発的なアクセス（月間数百万PV超、ピーク毎秒100リクエスト超）はCloudflareで吸収しきれない場合があります。その段階ではXServer VPSまたはクラウドへの移行を推奨します。本開発ではDB接続・ファイル保存先・キャッシュを設定で切り替えられる構成とし、移行時のアプリケーション改修を最小化します。

U-01　トップ・大喜利開催画面

優先度：A

目的

表示内容

- サービスロゴ（「ぼけばこ」）

- キャッチコピーと簡単な説明（例：「お題を出したら、24時間だけ大喜利スタート。」「Xでシェアして、みんなからボケを集めよう。」）

- 「ランダムなお題」ボタン（テンプレートからランダム提示）

- 開催者用合言葉入力欄（本人確認・別端末からの復旧用。通常の管理では毎回要求しない）

- 「24時間大喜利を開催する」ボタン

- 広告枠（上部・下部）

機能

- 入力文字数チェック、禁止文字・制御文字等の基本チェック

- NGワードチェック（投稿拒否ワードは即時エラー、要確認ワードは開催可・管理画面へ通知）

- 同一環境からの異常な連続開催の制限（閾値は運用設定で変更可）

- BOT／スパム対策（トークン検証、必要に応じてCAPTCHA表示）

- 開催確認モーダル（U-02）の表示

- お題

U-04　大喜利回答画面

優先度：A

目的

Xから来た参加者が、可能な限り少ない操作でボケを回答できるようにする。

表示内容

- お題（画面内で最も目立つ位置）

- 残り時間（例：「残り 18時間32分」。JavaScriptで1分ごとに更新）

- 現在の回答数（例：「現在 47回答」）

- 回答入力フォーム（匿名。名前・メールアドレス・登録不要。最大文字数あり、初期値140文字）

- 「回答する」ボタン（U-05 回答確認モーダルを表示）

- 通報ボタン（お題自体に問題がある場合）

- 広告枠（上部・下部）

仕様・ルール

- 回答前は他人の回答を表示しない（他人の回答に引っ張られない、見るだけの離脱を防ぐ、まず自分で考えて投稿してもらうため）

- 自分が回答した後は、他人の回答を閲覧可能とする（U-07）

- 「1人1回答」等の固定制限は設けない。会員登録がなく厳密な「1人」の判定が困難であり、複数の面白い回答を思いついたユーザーを不必要に制限しないため

- 同一環境から短時間に3回以上連続して回答する等、明らかに機械的・異常と判断できる投稿は制限対象とする。閾値は固定せず、運用設定画面で調整可能とする

- 判定材料：IPアドレス、Cookie、匿名ブラウザ識別子、投稿間隔、一定時間内の投稿回数を組み合わせる

- 正常な利用者を過度に制限するより、明らかな荒らし・BOT・大量投稿のみを防止することを優先する

目的

U-07　回答後・回答一覧画面

優先度：A

目的

回答後のユーザーが他の参加者のボケも楽しめるようにする。

表示内容

- お題

- 残り時間

- 回答数

- 回答一覧（新着順。ページング／もっと見る）

仕様・ルール

- 最低1件の回答を完了したブラウザのみ閲覧可能。未回答状態では回答一覧を表示しない（回答済み判定はブラウザ保存情報＋サーバー側の投稿記録で行う）

- 参加者による「いいね」「投票」「点数」「ランキング」は実装しない。回答の最終評価は開催者が行う

U-08　開催者専用画面

優先度：A

目的

開催者が自分の大喜利を管理し、最終的にベスト回答を選択する。一般ユーザーには公開しない。

表示内容

- 【開催中】お題、募集開始日時、募集終了日時、残り時間、PV、回答数、回答一覧、募集URL

- 【開催中】Xで再募集するボタン、募集URLコピーボタン、大喜利削除ボタン（確認ダイアログあり）

- 【回答一覧】各回答の本文、投稿日時、お気に入りボタン（お気に入りは一般公開しない）

- 【募集終了後】「募集終了。ベスト回答を選んでください。」を表示し、回答一覧から最大3件を選択。1件または2件のみでも結果確定可能。選択した回答に1位・2位・3位を設定

- 【選出期限】結果選出の残り時間（初期設定：募集終了から72時間）を表示

仕様・ルール

- 認証：開催時に発行した管理トークンを使用。同一ブラウザでは原則自動認証

- 別端末等の場合は、募集URLと合言葉を入力して本人確認・復旧を行う（合言葉照合の試行回数制限あり）

- 「結果を発表する」ボタン押下でU-09 結果確認モーダルを表示

7. 管理者向け画面仕様

管理画面は運営担当者のみがアクセスします。URLは推測困難なパスとし、必要に応じてIPアドレス制限を行います。

A-01　管理者ログイン

優先度：A

機能

- IDまたはメールアドレス＋パスワード認証

- ログイン試行回数制限（一定回数失敗で一時ロック）

- セッション管理（有効期限、ログアウト）

- 二段階認証（TOTP：Google Authenticator等）※本見積に含む

- 管理者アカウントの追加・権限設定（一般管理者／投稿元識別情報の閲覧権限を持つ上位管理者）

A-02　管理ダッシュボード

優先度：A

目的

サービスの利用状況だけでなく、「サービスが自力で拡散しているか」を確認する。

表示内容

- 本日PV、期間PV、累計PV

- 本日開催数、期間開催数、累計開催数

- 回答数、1開催あたり平均回答数

- 回答シェア数、募集シェア数、結果シェア数

- 通報数、非表示件数

- 期間指定（今日／昨日／7日／30日／任意期間）

最重要KPI

| **KPI** | **定義** | **例** |
| --- | --- | --- |
| 回答者 → 開催者転換率 | 回答完了ブラウザのうち、その後に新規開催したブラウザの割合 | 回答者10,000人 → 新規開催620人 → 転換率6.2％ |
| 1開催あたり派生開催数（派生開催係数） | 一定期間の開催数に対し、その参加者から生まれた新規開催数の比率 | 100開催 → 参加者から150開催発生 → 係数1.50 |

派生の紐付けは、回答完了画面・結果ページ等の「自分も大喜利を開催する」導線を経由した開催に派生元大喜利IDを保持することで実現します（S-06）。

- 操作：詳細、非表示、再公開、削除

- 詳細画面：回答一覧、通報履歴、開催者代理でのベスト回答変更（誤操作対応用）、結果ページキャッシュの再生成

8. 自動処理・システム機能仕様

S-01　24時間終了処理

- 各大喜利に starts_at（開始日時）と ends_at（終了日時）を保持する

- ends_at を過ぎた時点で、新規回答をサーバー側で受け付けない（画面表示に依存しない）

- cron（1分間隔）で ends_at を経過した「募集中」の大喜利を「結果選択待ち」へ遷移させ、選出期限（ends_at＋72時間）を設定する

S-02　72時間結果待ち処理

- cron（1分間隔）で選出期限を経過した「結果選択待ち」の大喜利を「結果未選出」として自動確定し、結果未選出ページ（U-12）のキャッシュを生成する

- 72時間は運用設定画面で変更可能

S-03　投稿監視・不正対策

基本方針：正常な複数回答は許可し、明らかな大量投稿・BOT・荒らしのみを制限する。

- 判定材料：IP、Cookie、匿名ブラウザID、投稿時刻、投稿間隔、一定期間の投稿回数

- 例：同一環境から数秒〜短時間のうちに3件以上連続投稿された場合などは、異常投稿候補として扱う。「3回」という数値はハードコードせず、運用設定で変更可能

- 制限方法：一時的な投稿制限、CAPTCHA表示、一定時間の投稿停止、管理画面への警告のいずれかを状況に応じて実施

- 開催・通報についても同様のレート制限を適用

S-04　通報処理

- お題および回答を通報可能とする（通報理由を選択式で取得）

- 一定条件（例：一定時間内に異なる環境からN件以上）を満たした場合、一時非表示 → 管理者確認へ移行する

- 単純に「通報3件なら必ず削除」とはせず、同一環境からの連続通報は1件として扱う等、悪意ある集団通報への対策を行う

- 通報時に管理者へメール通知（急増時はまとめて通知）

S-05　AI補助判定（GPT-5 nano）

詳細は第9章に定めます。NGワード「要確認」検知、通報、異常投稿判定のいずれかに該当した投稿のみをOpenAI APIへ送信し、判定結果を通報・モデレーション画面に表示します。

S-06　計測システム

単純なPVだけでなく、以下のイベントを記録し、サービスの自己拡散性を測定します。

| **イベント** | **記録タイミング** | **主な属性** |
| --- | --- | --- |
| 開催 | 大喜利作成時 | 大喜利ID、派生元大喜利ID、匿名ブラウザID |
| 募集シェア | Xシェアボタン押下時 | 大喜利ID、シェア種別 |
| 募集URL流入 | 回答画面表示時 | 大喜利ID、リファラ、UTMパラメータ |
| 回答 | 回答登録時 | 大喜利ID、回答ID |

9. AI補助判定（GPT-5 nano）仕様とコスト試算

9.1 方針

全投稿を常時AIで検閲することはせず、「疑わしい投稿のみ」をAIで補助判定します。AIは最終判断を行わず、管理者が通報・モデレーション画面で判断するための材料（判定ラベルと理由）を提供します。

| **項目** | **内容** |
| --- | --- |
| **使用モデル** | OpenAI GPT-5 nano（API） |
| **API料金** | 入力：$0.05（約7.5円）／100万トークン 出力：$0.40（約60円）／100万トークン ※ 1ドル＝150円換算。料金は変更される場合があります |
| **判定対象** | 以下のいずれかに該当したお題・回答 ① NGワード「要確認」に一致 ② 通報を受けた ③ 異常投稿判定（S-03）に該当 |
| **判定内容** | 「問題なし／要確認／非表示推奨」の3段階ラベルと、理由（個人攻撃・個人情報・差別・性的・権利侵害・その他）を構造化出力（JSON）で取得 |
| **判定タイミング** | 対象条件に該当した時点で非同期（cronキュー）に送信。ユーザーの投稿完了を待たせない |
| **結果の扱い** | 通報・モデレーション画面に表示し、優先表示の条件に加える。「非表示推奨」を自動非表示にするかどうかは運用設定で選択可能（初期値：自動非表示しない） |
| **送信データ** | お題・回答本文のみ。IPアドレス等の識別情報は送信しない。プライバシーポリシーに外部送信の旨を明記 |
| **安全弁** | 月間上限件数の設定、APIエラー時は「未判定」として管理者確認へ回す。APIキーは環境変数で管理 |
