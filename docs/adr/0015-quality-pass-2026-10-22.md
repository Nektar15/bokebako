## 決めたこと

1. **Vercel の仮置きは外部の MySQL 互換 DB につなぐ（D-01。ADR 0008-3 を変える）**。SQLite（`/tmp`）はインスタンスごとに別の DB になり、同時アクセスの多くが 404 になる（実測 40 件中 29 件）。`api/index.php` は、DB が SQLite でなければインスタンスごとに1回 `vercel:prepare`（マイグレーション、空のときだけ DevSeeder）を流す。TLS が必須の DB は `database.default.sslCA` に CA 証明書のパスを書く（`Config\Database`）。DB のアカウントと接続情報は発注者側で用意する（`docs/vercel.md` 2-2）。SQLite のままでも従来どおり動く
2. **開催者ページは非公開のまま（D-02）**。公開プロフィールは作らない（SPEC 1.4・11章で対象外。匿名のサービスのため）。代わりに「このブラウザで開催した大喜利」の一覧を U-01 と U-08 に出す。localStorage の開催者トークン（`bk:host:{slug}`）を `POST /api/v1/hosted` に送り、トークンが今も正しいものだけ返す。ほかの人には見えない
3. **合言葉は必須、4〜32 文字（D-03。ADR 0004-8 の【仮】「任意・4文字以上」を変える）**。開催時と本人確認時で同じ整え方をする（`App\Libraries\Passphrase`：前後の空白（全角を含む）と見えない文字を取り、NFKC でそろえる）。bcrypt は 72 バイトまでしか見ないので SHA-256 を通してから `password_hash()` する（印 `v2$`）。それより前に作った大喜利の合言葉（`Text::clean()`・`trim()` の形式）もそのまま照合できる。合言葉なしの既存の大喜利はそのまま（DB の変更なし）
4. **並び替えは新着順・古い順（D-04）**。同じ日時は ID で順を決める。既存のインデックス（`oogiri_id, status, created_at`）を使う。人気順は、閲覧者の「いいね」を作るか決めてから
5. **存在しない・非表示の回答 URL は 404（D-05）**。非表示・削除中の大喜利の回答 URL も 404（以前は募集 URL へ移していた）
6. **GA4 には指示書 第9章のイベント名で送る（D-06）**。自前の events テーブルの名前（A-02 の KPI が使う）はそのまま。`share_complete` は Web Share API の共有シートで送り終えたときだけ送る（X の投稿画面では投稿したかが分からないので送らない）。開催完了・回答完了は sessionStorage の印で、同じタブで二度送らない（CODING_RULES 9-2 の保存キーに追加）。合言葉・回答の本文などはパラメータに入れない
7. **ほかの人の回答のシェア文は別のひな形 `tpl_answer_other`**（BUG-008。既定「このボケ好き：{answer}」。A-10 で編集できる）。自分の回答（U-06、U-07 の「あなたの回答」）だけ `tpl_answer`（「俺の回答」）。共有キャッシュの U-10・U-12 は本人かを付けないので、ほかの人の回答として扱う
8. **規約・ガイドラインは U-02 の上に重ねたシートで読む（BUG-007）**。ページを取りに行き本文だけ入れる。閉じると U-02 に戻る。JS なしでは別タブで開く
9. **シェアは X の投稿画面を主にし、使える端末では OS の共有シートも出す（BUG-003）**。開催者が自分の募集 URL（U-04）を開いたときも募集のシェアを出す（U-03 を開けなかったときの導線）
10. **E2E テストは Playwright（`tests/e2e/`、独自の package.json）**。本体の依存には足さない（Vercel の `package.json` は OGP 用のまま）

## 影響

- `.env` に `database.default.sslCA`（任意）
- 運用設定に `tpl_answer_other`（既定値あり。マイグレーション不要）
- 新しい API：`POST /api/v1/hosted`
- デプロイ後は、ページキャッシュ（`writable/cache/`）を消すと、キャッシュ配信のページにも新しい計測が入る（消さなくても TTL で入れ替わる）
