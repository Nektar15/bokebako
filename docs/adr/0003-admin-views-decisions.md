# 0003 工程2（管理画面の外側）で仮置きした判断

- 日付：2026-10-20
- 状態：採用（「仮」の項目は発注者の確認待ち）

## 決めたこと

1. **A-05 の操作ルートのキーを `{oogiri|answer}-{id}` にする**（`/moderation/(:segment)/resolve` など）。工程0では `(:num)` だったが、通報の対象は「お題」と「回答」の2種類で ID だけでは特定できない。
2. **ModerationItem は DB の1行ではなく、対象ごとに通報・NG検知・異常投稿・AI判定をまとめた形**にする（`app/Entities/ModerationItem.php`）。工程4で `ModerationService` がこの形に組み立てる。
3. **仮認証の管理者は `?role=general` で一般管理者に落とせる**（development / testing 限定。production では無視）。A-04 の「投稿元」列の出し分けをブラウザとテストで確認するため。A-01 実装時に仮認証ごと削除する。
4. **管理画面の操作は「1ボタン＝1フォームの POST」**にし、確認が要るものだけ `<dialog>` を挟む（`partials/admin_action_form`）。JS が動かなくても操作できる。
5. **絞り込み・タブ・一覧の1件選択（A-05・A-09）はすべてクエリ文字列**（`?status=` `?filter=` `?item=`）で表現する。URL を共有すれば同じ画面が開ける。
6. **A-06 のカテゴリーは固定の配列**（`NgWordFixture::CATEGORIES`、見本の7種）。管理方法は未確定事項11として追加。【仮】
7. **A-07 の掲載場所は1広告につき1つ**（上部または下部）。デザインはチェックボックスだが、仕様書の登録項目は「掲載場所」単数のためラジオにした。【仮】
8. **A-10 の運用設定に、仕様書にない3項目を追加**：制限方法（S-03 の「一時制限／CAPTCHA／投稿停止」の選択）、停止する時間、急増の通知件数、AI判定の対象。いずれも仕様書本文の記述をデザインどおりに設定化したもの。数値の上限・下限は `SettingService::INT_RANGES` に仮置き。【仮】
9. **一覧の通報数を強調する下限**（A-03：5件、A-04：3件）は見本の値を定数にした（運用設定にはしない）。【仮】
10. **ダッシュボードの「今日」は前日分までの集計**（毎日 4:00 の日次バッチ。SPEC 9「生ログを直接読まない」）。棒グラフは View で計算しないため、Service が SVG の座標まで計算する。
11. **PHPStan の `ENVIRONMENT`** は `dynamicConstantNames` で動的扱いにする（工程1の修正時）。bootstrap で `'testing'` に固定されるため、環境判定が「常に false」と誤検知されていた。

## 理由

- 1・2：仕様書 A-05 は「対象（お題／回答）」を1つの画面で扱う。
- 3：CODING_RULES 7-1「仮管理者は上位管理者」のままでは一般管理者の表示を確認できない。権限を下げる方向なので安全側。
- 4・5：CODING_RULES 8-3「JS が動かなくても送信できる」を管理画面にも適用した。
- 6〜9：仕様書に値や扱いがなく、デザインの見本を正として仮決めした。

## 影響

- 工程4で `reports` テーブルの集計を `ModerationItem` の形にする処理が必要
- `docs/FEATURES.md` 6章に未確定事項 11〜13 を追加
- 部品（`partials/admin_*`）の値は呼び出し間で残るため、省略できる引数を作らず毎回すべて渡す（View 契約に明記）
